# 기기 내 경기 사례 비교 실행

이 경로는 설치한 모델과 앱 자료를 기기에서 불러와 검색하고 WebAssembly 엔진으로 생성한다. 허브나 Ollama는 필요하지 않으며 기존 서버 방식도 선택할 수 있다. 첫 설치에는 인터넷과 여유 저장 공간이 필요하다. 설치 중 취소할 수 있고, 다운로드가 중단되거나 파일 크기·SHA-256이 맞지 않으면 불완전한 파일을 제거한다. 다시 열어 설치하거나 삭제 후 재설치할 수 있다. 브라우저 저장소 정리·기기 초기화 등으로 모델이 지워질 수 있으므로 영구 보관을 보장하지 않는다.

모델은 [Qwen2.5-3B-Instruct GGUF](https://huggingface.co/Qwen/Qwen2.5-3B-Instruct-GGUF/tree/7dabda4d13d513e3e842b20f0d435c732f172cbe), revision `7dabda4d13d513e3e842b20f0d435c732f172cbe`, `qwen2.5-3b-instruct-q4_k_m.gguf`, 2,104,932,768 bytes, SHA-256 `626b4a6678b86442240e33df819e00132d3ba7dddfe1cdc4fbb18e0a9615c62d`다. Qwen은 한국어를 포함한 다국어를 지원한다고 안내하지만 이 앱에서 한국어 사례 비교 품질은 평가하지 않았다. [모델 라이선스](https://huggingface.co/Qwen/Qwen2.5-3B-Instruct-GGUF/blob/7dabda4d13d513e3e842b20f0d435c732f172cbe/LICENSE)는 연구·평가 목적의 비상업적 사용만 허용하며 상업적 사용에는 별도 허가가 필요하다. 교육 사용이라는 이유만으로 허용 여부를 단정하지 않는다.

[wllama 3.13.0](https://github.com/ngxson/wllama)은 llama.cpp의 브라우저 WebAssembly 바인딩이다. 앱은 동일 출처의 WASM을 사용하며 교차 출처 격리가 활성화되고 엔진이 지원할 때 최대 4개 스레드, 그렇지 않으면 단일 스레드를 사용한다. 지원하는 기기에서는 WebGPU를 자동으로 사용할 수 있고, 그렇지 않으면 CPU를 사용한다. 실제 Android WebGPU 동작은 검증하지 않았다. 기본 엔진에는 JSPI와 MEMORY64가 필요하며, 없으면 자체 보관한 호환 엔진으로 전환한다. WebGPU나 멀티스레드 격리 헤더는 필수가 아니지만, 보안 출처와 OPFS, Web Locks, WebAssembly SIMD 및 Worker가 필요하다. 모델을 여는 동안 취소를 요청하면 엔진이 현재 작업을 정리할 때까지 시간이 걸릴 수 있다. WebView·브라우저 버전, 메모리와 저장소에 따라 사용이 불가능하거나 느릴 수 있다. 2.1GB 파일 외에도 모델과 문맥을 위한 추가 메모리가 필요하며 낮은 사양에서는 로딩이 실패하거나 앱이 종료될 수 있다. 지원 조건만 확인되었다고 실제 실행을 보장하지 않는다.

검색 자료는 `node scripts/build-tactics-local.cjs`로 기존 서버 자료와 수용 manifest를 검증해 재생성한다. 평가 질문은 포함하지 않는다. 서버와 같은 조건 검색 및 출처 ID 검증을 사용하고, 텍스트만 입력해도 모델 없이 원자료를 즉시 검색할 수 있다. 선택 기능에서 모델에 전달하는 후보는 토크나이저로 최대 512 입력 토큰과 96 출력 토큰 예산을 확인해 후보 단위로 줄인다. 하나도 들어가지 않으면 오류를 표시한다. 새 출처 ID나 잘못된 JSON은 거부한다. 오류 발생 시 생성하지 않은 답변을 AI 답변으로 대체하지 않는다.

Chromium에서 별도의 19MB 소형 GGUF로 실제 WASM과 구조화 응답 문법을 확인했다. 이 작은 모델을 이용한 엔진 동작 확인은 3B 모델 정확도·속도·메모리 또는 Android 실기기 검증이 아니다. 실제 3B의 짧은 독립 생성과 오프라인 앱 사례 생성은 확인했다. 아래 실측에서는 답변 품질이 실패했으며 Android 기기 재실행·비행기 모드, 학교 환경 및 450개 문항의 사람 관련성·모델 선택 검증은 남아 있다.

배포물 출처: `@wllama/wllama`와 `@wllama/wllama-compat` npm 3.13.0의 MIT 라이선스 ESM·WASM을 `vendor/wllama-v3`에 보관한다(패키지 SHA-512 각각 `ZvoRdQAn+E+18EvQ9qS036gudiI9rbZRBJgG/qNICPPwrA0Y6SMMdbziz/j7K/0WxcbJlhaRraVIYsnEy732NA==`, `MSWwyzVXpwkstvIGzOsQ9jlRm8kY5S5J0Gdw4E6M9mXqhgO/5tj+YNfxSoqN1GvsAOwui95JPtwX3hO6VZkbzg==`). 모델 파일 자체는 저장소에 넣지 않는다. 다운로드 무결성 검증은 MIT 라이선스 `@noble/hashes` 1.7.1의 스트리밍 SHA-256을 사용한다. 모델 다운로드와 실행, 삭제는 같은 출처의 다른 탭에서도 동시에 진행되지 않는다.

수동 재현(무거운 검사): 고정 revision의 공식 GGUF를 별도로 확보한 뒤 `node scripts/manual/tactics-local-3b.cjs /path/to/qwen2.5-3b-instruct-q4_k_m.gguf /tmp/pe-3b-result.json`을 실행한다. `PE_TEST_ISOLATION=1`을 앞에 붙이면 격리 헤더와 실제 격리 여부를 확인한다. 시험용 `PE_TEST_HARDWARE_CONCURRENCY=2` 등으로 스레드 상한을 재현할 수 있으며 이는 실제 기기 성능 측정이 아니다. Playwright와 Chromium이 필요하고, 스크립트는 파일의 크기·SHA-256을 먼저 확인한다. 격리한 브라우저 프로필에서 해당 파일을 로컬 HTTP로 전달해 앱의 설치·검색·생성을 실행하고, 네트워크를 차단해 새로고침 후 다시 실행한다. 테스트 결과와 단계별 시각은 지정한 JSON에 기록하며 프로필은 종료 시 삭제한다. 기본 테스트는 대형 파일을 다운로드하거나 이 검사를 실행하지 않는다. 런타임·모델·검색 자료 변경 후에는 다시 검증해야 한다.


실측 중간 기록: Debian 13 컨테이너의 Chromium 155, CPU 단일 스레드에서 공식 3B 모델의 앱 설치(로컬로 전달한 공식 파일의 크기·SHA 확인)와 WASM 로딩은 성공했다. 최적화 전 첫 사례 비교는 약 20분 42초에 응답이 없어 중단했다. 별도 짧은 10토큰 입력·9토큰 출력 실험은 모델 로딩 약 22.8초, 첫 토큰 약 21.2초, 생성 약 37.3초였다. 이 시간은 해당 컨테이너의 기록으로 Android 기기 성능을 뜻하지 않는다. 3.13.0 전환 후 실제 앱의 1127토큰 사례 질문을 단일 스레드로 시험했지만 20분 제한 내 응답하지 않아 종료했다. 이후 중복 제거와 입력 처리 단위 조정 후 기존 설치 모델을 오프라인 재시작한 2스레드 Chromium 사례 시험에서 입력 예산 862토큰(여유 4토큰 포함), 실제 입력 858토큰·출력 92토큰에 입력 처리 686.0초·생성 111.9초, 모델 로딩 포함 약 819.6초 후 JSON 응답을 받았다. 브라우저 재시작 후 오프라인에서 SW v42·설치 상태·검색 복구를 확인했으나 재시작 후 생성은 실행하지 않았다. 네트워크 요청은 관찰되지 않았고 선택 ID 두 개는 후보에 포함됐다. 그러나 설명은 문장 중간에 끊겼고 프리킥 사례를 코너킥처럼 묘사했으며 비교 한계도 단순히 “한계”에 그쳤다. 구조·출처 ID 확인은 통과했지만 답변 품질은 실패이며, 이 결과는 수업 실사용 준비나 Android 성능을 뜻하지 않는다. wllama 2.3.3에서는 문법 상태가 갱신되지 않는 결함이 확인되어 사용하지 않는다. 3.13.0의 제한된 JSON 문법은 작은 모델에서 유효한 JSON과 후보 ID를 생성하는지 확인했다. 기존 서술 생성의 품질 실패 이후 모델은 ID만 선택·정렬하고, 화면의 관찰·지원 조건·빠진 조건과 한계는 원자료에서 제공하도록 변경했다. ID 전용 JSON과 제공된 후보 범위·중복은 생성 후 검사하며 실패하면 오류를 반환하고 검색 자료는 유지한다. 이 변경의 실제 3B 오프라인 선택을 아래와 같이 확인했다.

모델 입력 길이는 Apache-2.0 `@huggingface/tokenizers` 0.2.0과 Qwen 공식 tokenizer 파일을 로컬에서 읽어 계산하며 안전 여유 4토큰을 더한다. 토크나이저는 `Qwen/Qwen2.5-3B-Instruct` revision `aa8e72537993ba99e69dfaafa59ed015b17504d1` 원본 그대로다. `tokenizer.json` SHA-256은 `c0382117ea329cdf097041132f6d735924b697924d6f6fc3945713e96ce87539`, `tokenizer_config.json`은 `5b5d4f65d0acd3b2d56a35b56d374a36cbc1c8fa5cf3b3febbbfabf22f359583`이다. 한국어·ChatML 특수 토큰·숫자 세 샘플의 토큰 ID는 실제 GGUF 엔진 토큰화 결과와 대조해 일치했다.

3.13.0으로 동일 컨테이너에서 모델을 다시 열고 짧은 10토큰 입력·10토큰 출력 실행을 확인했다. 로딩은 약 22.16초, 입력 처리는 9.62초, 출력은 10.46초, 생성 전체는 약 20.14초였다. 이는 단일 CPU 스레드의 짧은 독립 실험이며 실제 사례 비교 응답이나 Android 성능을 검증한 수치가 아니다. 실제 앱 질문은 이보다 훨씬 긴 입력이어서 수업에서 사용하기에 느릴 수 있다.

정적 PWA를 제공하는 서버가 `Cross-Origin-Opener-Policy: same-origin`과 `Cross-Origin-Embedder-Policy: require-corp` 응답 헤더를 설정하고 브라우저가 교차 출처 격리를 지원하면, 앱은 엔진이 WASM 스레드 지원을 확인한 뒤 최대 4개 스레드를 사용한다. 이 서버는 앱 파일을 제공하는 역할이며 설치 후 추론 서버로 사용되지 않는다. 격리 설정은 외부 리소스의 CORS/CORP 조건과 팝업·다른 창 연동에 영향을 줄 수 있으므로 배포 환경에서 함께 점검해야 한다. Android 앱은 신뢰된 WebViewAssetLoader 앱 자산 응답에 COOP/COEP/CORP 헤더를 설정한다. 실제 Android WebView에서 격리·멀티스레드·카메라 및 서버 연동이 함께 작동하는지는 검증하지 않았다. 외부 모델 다운로드와 서버 연결에는 해당 출처의 CORS 허용이 여전히 필요하다. 격리되지 않은 기기에서는 한 스레드로 실행한다.

2026-11-15 후속 변경: 학생과 교사는 전술판 없이 텍스트로 자료를 검색할 수 있다. 빠른 자료 검색은 모델이나 인터넷이 필요하지 않다. 선택 기능은 실제 3B가 원자료의 ID만 선택하며, 모델이 경기 사실이나 비교 한계를 자유롭게 서술하지 않는다. 검색 결과와 모델 선택 결과는 서로 구분한다. 이전 3B 자유서술의 사실 혼동 및 지연은 위 실패 기록 그대로이며, 바뀐 ID 선택 경로는 아래 기록처럼 한 번 실측했다. 추가 질문에서의 선택 품질·다른 기기 속도와 Android 실기기 결과는 별도로 검증해야 한다.


ID 선택 방식 실측: 동일 Debian 13·Chromium 155 격리 환경에서 기존 설치 모델을 오프라인으로 열고 독립 질문 “코너킥 헤더”를 시험했다. 실제 2스레드, 입력 198토큰·출력 17토큰, 입력 처리 162.1초·출력 25.7초, 모델 로딩 포함 약 206.6초였다. 외부 요청은 관찰되지 않았고 모델의 SCG-01·SCG-03은 제공 후보에 속한 서로 다른 ID였다. 두 카드의 설명은 모델 문장이 아니라 원자료의 지원 범위다. SCG-03은 코너킥이 아닌 프리킥 장면으로 부분 관련·미확인 조건을 유지한다. 이 1회 구조·출처 검사만으로 선택 정확도나 학교 현장 품질을 보장하지 않으며, 수 분의 지연은 해당 시험 환경에서 실사용의 제약이다. Android 실기기 검증과 450개 질문의 사람 관련성·모델 선택 평가는 아직 남아 있다.
