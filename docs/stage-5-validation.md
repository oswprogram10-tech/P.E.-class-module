# 5단계 — 기기와 실제 수업 검증

## 현재 판정

- **F02 합성 영상 회귀 검증**: 개발용 브라우저에서 통과했다. `tests/browser-clips.cjs`는 최신 클립을 `createdAt` 기준으로 선택하도록 유지하고, 비동기 seek 검사를 보강한 뒤 **5회 연속 실행해 5/5 통과**했다. 제품 코드는 변경하지 않았다. 아래 기준별 결과는 실제 실행 출력이다.
- **F01 실기기 검증**: 갤럭시 탭 A9+와 저사양 Android 기기에 접근할 수 없어 **미실행**이다. 결과표만 준비했다.
- **F03 수업 파일럿**: 파일럿 교사·모둠과 학교의 안내·동의 절차가 확인되지 않아 **미실행**이다. 기록표만 준비했다.
- 따라서 **5단계 전체는 완료가 아니다.** F02의 자동화 결과로 F01·F03의 실기기·현장 결과를 대신하지 않는다.

이 문서의 “통과”는 Windows의 Chrome, 가상 카메라, 테스트가 띄운 임시 로컬 HTTP 서버에서의 결과다. 실제 Android Chrome·카메라·저장소·발열·배터리 결과가 아니다.

### 데이터 격리와 합성 자료

- 모든 브라우저 테스트는 테스트 파일마다 새 Playwright 브라우저와 새 컨텍스트를 띄운다. IndexedDB·localStorage는 그 임시 프로필 안에서만 생성되고, 실행이 끝나면 브라우저와 함께 사라진다. 개발 PC의 실제 앱 데이터를 읽거나 덮어쓰지 않는다.
- 카메라는 Chrome 가상 장치를 사용한다. 실제 학생이나 교실을 촬영하지 않는다.
- `tests/browser-clips.cjs`는 100ms 간격의 합성 프레임 35초를 만들고, 1초마다 다른 단색과 `source N.0s` 텍스트를 넣는다. 선택 구간의 시작·중간·끝 색을 저장 파일 재생 화면에서 다시 읽어 비교한다.
- `tests/browser-data.cjs`는 합성 JPEG를 암호화해 가상 클립을 만들고, 이름도 `가상학생`·`정상가상학생`만 사용한다.

### 이번에 보완한 테스트

`tests/browser-clips.cjs`는 기존 5초 단일 검사를 5·15·30초 순차 검사로 확장하고, 선택 시작 시각에서 각 출력 시점의 원본 초를 계산해 시작·중간·끝 색을 비교하도록 했다. 또한 기존 클립이 있는 상태에서 공간 부족과 트랜잭션 중단을 다시 주입해 클립 수가 변하지 않는지 확인한다.

IndexedDB의 `getAll()`은 생성 시각순이 아니라 키(ID)순으로 반환하므로, 방금 저장한 클립을 `records.at(-1)`로 가정하지 않는다. 저장된 레코드 중 `createdAt`이 가장 큰 클립을 선택해 현재 저장 작업의 결과를 비교하도록 고쳤다. 제품 코드는 변경하지 않았다.

### 비동기 seek 검사 안정화

검토 환경(Linux Chromium 155)에서 5회 중 1회, 영상 seek 뒤 이전 프레임 색을 읽는 실패가 보고됐다. 현재 실행 환경(Windows Chrome 156)에서는 같은 실패가 재현되지 않았지만, 기존 검사에는 다음과 같은 경합 가능성이 있었다.

- `video.currentTime`을 먼저 설정하고 `seeked` 처리기를 나중에 등록해, 빠른 seek가 처리기 등록 전에 끝날 수 있었다.
- `seeked` 직후 캔버스에서 읽어, 새 프레임이 합성되기 전 이전 프레임을 그릴 수 있었다.
- 표본이 0·2·4.9초처럼 정수 초 경계나 경계에 가까운 시점이어서, 한 프레임 차이로 인접 색을 읽을 수 있었다.

테스트를 다음과 같이 보강했다.

- `currentTime`을 설정하기 전에 `seeked` 처리기를 등록한다.
- `seeked` 후 `video.seeking === false`이고 `currentTime`이 목표 시각의 0.1초 이내인지 확인한다. 충족하지 못하면 목표 시각·실제 시각을 담아 실패한다.
- `requestVideoFrameCallback`으로 목표 프레임 표시를 기다린 뒤 캔버스에서 읽는다. `mediaTime`이 목표에서 0.2초 이상 벗어나면 다음 프레임을 기다린다.
- 시작·중간·끝 표본을 원본 색이 바뀌는 정수 초 경계에서 0.5초 떨어진 내부 시점으로 잡는다. 장면 기대값과 픽셀 허용치(채널당 10)는 그대로 유지했다.

수정 후 5회 연속 실행에서 5/5 통과했고, 각 표본의 `currentTime`과 `mediaTime`이 목표 시각과 일치했다. 제품 코드는 변경하지 않았다. 이 실패는 제품의 프레임 선택·인코딩 결함이 아니라 테스트의 비동기 seek·프레임 합성 타이밍 경합으로 판단한다. Linux Chromium 155에서의 반복 실행 결과는 아직 없으며, 이 문서의 5/5는 Windows Chrome 156에서의 결과다.

`ffprobe`/FFmpeg가 있는 환경에서는 같은 테스트가 WebM 색 범위·색 공간과 압축 해제 픽셀까지 추가로 검사한다. 현재 환경에는 두 도구가 없어 이 부분은 건너뛰었고, Chrome 재생 기반 검사만 통과로 기록했다.

### 남은 F02 제약

- `tests/browser-smoke.cjs`의 WebM 패킷 끝 시각·오디오 트랙 부재 검사는 `ffprobe`가 없어 실행하지 못했다. Chrome이 보고한 길이와 화면 픽셀은 확인했지만, 패킷 수준의 30초 상한을 이번 환경에서 다시 확인한 것은 아니다.
- 실제 Android Chrome의 WebCodecs 지원·인코딩 속도·저장 대기는 F01에서 확인해야 한다.
- 자동화는 합성 장면만 사용하므로 실제 카메라의 노출·색·압축 차이는 다루지 않는다.

### F01 대기 사유와 남은 준비

- 실제 갤럭시 탭 A9+와 저사양 기기를 확보하지 못했다.

## F03 — 수업 파일럿 기록표 (미실행)

### 시작 전 확인

- 학교의 학생 영상 수집·보관, 기기 공동 사용, 초상권·개인정보 안내와 동의 절차가 확인되기 전에는 파일럿을 시작하지 않는다.
- 파일럿 로그와 개발 자료에는 학생 이름·번호·실제 영상·식별 가능한 정보를 수집하지 않는다. 아래 표의 기록 항목만 남긴다.
- 교사 1명·모둠 1개부터 시작하고, 수업을 막는 문제를 해결한 뒤 적용 모둠을 늘린다.

### 기록 항목

- **교사 준비 시간**: 앱 실행부터 지연 영상이 보일 때까지. 4단계의 준비 1분 측정 방법을 재사용한다.
- **저장 대기 시간**: 저장 버튼을 누른 뒤 목록에서 확인 가능할 때까지.
- **조작 실수**: 학생·교사가 다시 시도한 횟수와 종류. 개인 식별 정보 없이 횟수만 기록한다.
- **학생 동작 확인 용이성**: 학생이 지연 영상으로 자기 동작을 확인하기 쉬웠는지에 대한 교사 관찰. 학생 이름·영상은 기록하지 않는다.

### F03 대기 사유와 남은 준비

- 파일럿에 참여할 교사·모둠과 수업 일정이 정해지지 않았다.
- 학교의 안내·동의 절차 확인 상태가 확인되지 않았다.
- F01의 실제 기기 결과와 F02의 자동화 결과를 바탕으로 파일럿에서 확인할 항목을 좁힌 뒤 시작한다.

## 변경하지 않은 것

- 제품 코드의 지연·선택·저장·PIN·만료·삭제 동작과 허용치. 테스트를 통과시키기 위해 기준을 넓히지 않았다.
- 실제 학생 영상·이름·번호·식별 가능한 정보. 합성 자료만 사용했다.
- 앱 런타임 의존성, 외부 서비스, 배포·호스팅, 6단계 작업.
- 커밋·푸시. 이번 작업은 `phase-5` 작업 트리 변경으로만 남겨 두었다.
