# 이 세션의 팀 운영 흐름

설정일: 2026-11-05

이 문서는 사용자가 요청한 Sol 총괄, Terra 구현, Luna 검증·문서 팀의 역할과 협업 절차를 기록한다. 현재 저장소 `/workspace/P.E.-class-module`의 `work` 브랜치를 그대로 사용한다.

## 공통 목표와 판단 근거

- 후속 개발 순서와 완료 기준은 [세션 목표](session-goals.md)의 S1~S5, 34개 세부 작업을 따른다.
- 기존 첫 출시 요구사항과 작업 ID는 [구현 계획표](implementation-plan.md)를 따른다. 과거의 다음 작업 안내보다 세션 목표의 최신 순서를 우선한다.
- 구현·개발용 검증·실기기 대기의 구분은 [작업 상태표](task-status.md)와 실제 코드·최신 검증 근거를 따른다.
- 현재 구현 범위는 세션 목표의 최신 실행 기록과 사용자의 명시적 요청을 따른다. 아래 S1.1~S1.2 배분은 최초 팀 준비 당시의 계획이다.

## 역할과 현재 에이전트

| 역할 | 실제 지정 모델 | 현재 대화의 에이전트 ID | 책임 |
| --- | --- | --- | --- |
| Sol 총괄 | `gpt-6.1-sol` | `/root/sol_current` | 목표 분해, 작업 배분, 파일 소유권 지정, 통합 검토, 증거에 근거한 완료 판정 |
| Terra 구현 | `gpt-6.1-terra` (high) | `/root/sol_current/terra_current` | 복잡한 코드 구현·수정·문제 진단, 변경 근거와 자체 점검 결과 보고 |
| Luna 검증·문서 | `gpt-6-luna` (medium) | `/root/sol_current/luna_current` | 범위가 명확한 검사, 테스트 결과 분석, 문서와 체크리스트, 구현과 독립된 관점의 검증 |

위 표는 새 게시 환경의 연결을 확인한 현재 팀이다. `/root/sol_lead`와 그 하위 에이전트 경로는 이전 환경의 과거 팀 기록이며, 현재 환경 작업을 위해 재개하지 않는다. 아래 과거 실행 기록의 경로는 당시 담당자를 나타낸다.

`/root`는 사용자 요청을 전달하는 창구이고 개발 작업의 지휘와 통합은 Sol이 맡는다. 역할은 운영 기준이며 기능 개발을 막는 제한이 아니다. 후속 개발 요청을 받으면 Sol이 실제 작업을 나누고 결과를 통합한다. 간단한 통합 수정과 최종 검토는 Sol이 직접 수행할 수 있다.

## 작업을 배분하고 검토하는 순서

1. Sol이 해당 세부 작업의 목적, 선행 조건, 보존할 동작과 완료 기준을 정리한다. 시작 시 적용되는 `AGENTS.md`, 현재 브랜치, 기존 미커밋 변경을 확인한다.
2. Sol이 담당자별로 작업 ID, 산출물, 편집할 파일, 검증 범위와 인계 조건을 지정한다. 쓰기 소유자는 파일마다 한 명만 둔다. 같은 파일이 필요하면 앞 작업의 인계가 끝난 뒤 소유권을 넘긴다.
3. Terra는 지정 범위의 구현과 자체 점검을 수행하고 변경 파일, 동작 설명, 실행 명령과 결과, 실패·미확인 항목을 보고한다. 범위 밖 변경이나 다른 담당자의 파일이 필요하면 Sol에게 먼저 알린다.
4. Luna는 합의한 완료 기준과 실패 시나리오를 기준으로 독립적으로 확인한다. 구현자의 설명과 기존 통과 기록만으로 검증 완료를 선언하지 않는다. 실행하지 않은 검사는 미실행으로 남긴다.
5. Sol은 실제 변경과 검증 근거를 통합 검토한다. 발견된 문제는 파일 소유권을 다시 정해 수정하고, 해당 변경에 필요한 검사를 수행한다. 이유 없이 같은 검사를 반복하지 않는다.
6. Sol이 완료 범위, 실행한 검사, 실패·미실행·외부 조건 대기와 다음 작업을 정리한다. 개발용 브라우저 결과를 Android 실기기 결과로 바꾸지 않는다.

읽기 전용 조사나 겹치지 않는 파일 작업은 병렬로 진행할 수 있다. 공유 작업 공간에서 다른 담당자의 변경을 되돌리거나 기존 미커밋 변경을 덮어쓰지 않는다. 기존 파일이 있으면 내용을 확인하고 이어서 수정한다.

## 토큰을 아끼는 배분 기준

세션 목표의 [남은 작업 배분표](session-goals.md#남은-작업의-토큰-효율별-배분)를 기본으로 한다. 작고 낮은 위험의 변경은 Sol이 처음부터 관련 테스트까지 맡는다. Terra는 구현 파일 소유권이 분리되거나 Sol이 통합하는 동안 독립 경계 테스트를 만들 수 있을 때만 추가한다. Luna는 정확도·개인정보·평가 규칙처럼 결과 판정이 민감한 작업에서 정해 둔 질문을 확인한다.

통합 전에는 담당자가 변경된 영역의 집중 테스트만 돌리고, 전체 회귀는 통합 후 한 번만 실행한다. 같은 결과를 세 모델이 되풀이하지 않는다. 실패나 코드 변경이 생기면 영향받은 검사만 다시 돌린다. 병렬화로 대기 시간을 줄일 근거가 없거나 공유 파일을 함께 수정해야 하면 순차적으로 처리한다.

담당자의 결과 보고는 다음 항목을 포함한다: 작업 ID와 변경 파일, 구현한 범위, 실제 실행한 명령과 결과, 발견한 문제, 미실행·외부 대기 조건, 다음 담당자에게 넘길 내용. 어떤 모델도 테스트 통과를 보장하지 않는다.

## 다음 구현 묶음의 배분 기준

S1.1에서 Terra는 기존 서비스 워커 설치·활성화·캐시·페이지 버전 혼합 위험을 조사하고, 구버전 사용 중 새 버전이 제공되는 상황을 자동 검사할 수 있도록 준비한다. Luna는 구버전·신버전의 구분, 설치·활성화·캐시 실패, 실행 중 상태별 전환과 데이터 보존을 확인할 검증 관점을 정리한다. Sol이 코드 조사 후 실제 파일별 소유권과 검사 범위를 확정한다.

S1.2에서는 촬영·장면 선택·인코딩·DB 저장 중 업데이트를 강제로 적용하지 않고, 안전한 시점에 사용자의 동작으로 적용하도록 구현·검증한다. 기존 PIN·암호화 클립을 보존하는지 확인한다. 구현 담당자의 자체 점검과 Luna의 독립 검증을 거쳐 Sol이 완료 여부를 판정한다. 이 배분 기준은 준비 계획이며 현재 구현 착수를 뜻하지 않는다.

## 완료 상태와 외부 조건

| 상태 | 기록 기준 |
| --- | --- |
| 완료 | 명시한 범위의 산출물과 필요한 검증 근거를 확보함. 확인한 환경과 한계를 함께 기록 |
| 부분 완료·실패 | 완료 기준 중 충족한 범위와 남은 결함 또는 실패 원인을 구분 |
| 미실행 | 아직 시작하지 않은 구현·검사. 과거 통과나 계획으로 대신하지 않음 |
| 외부 조건 대기 | 실제 기기·계정·배포 접근·공식 자료 등 필요한 조건이 없음. 가능한 로컬 작업은 계속 진행 |

실제 Android 검증은 당분간 어렵다는 기존 조건을 존중하며 같은 확인 요청으로 개발을 멈추지 않는다. 실제 40분 촬영과 합성 시각 40분 검사는 별도 근거로 유지한다. 사용자 승인이나 접근이 필요한 외부 배포·권한은 팀 구성만으로 확보됐다고 추정하지 않는다.

## 이번 준비 작업의 상태와 한계

- Sol·Terra·Luna가 공통 목표 문서를 확인했고, 적용 경로에서 `AGENTS.md`는 발견하지 못했다. 이후 지침이 추가되면 작업 전에 다시 적용한다.
- Terra·Luna는 준비 상태를 보고했으며 후속 작업을 받을 수 있도록 유지한다. 이번 작업에서 앱 구현, 서버 시작, 앱 테스트 실행은 하지 않는다.
- 이번에 작성하는 파일은 이 문서뿐이다. 기존 신규 `docs/session-goals.md`와 `docs/implementation-plan.md` 첫머리의 연결 2줄은 보존한다. Git commit/push와 클라우드 설정 변경은 하지 않는다.
- 이 구성은 **현 대화의 에이전트 구성**이다. 계정 기본 모델, 새 대화에서의 자동 실행, 클라우드 머신 자체 설정을 바꾸지 않는다. 새 대화에서는 이 문서를 읽고 에이전트를 다시 구성해야 하며 현재 에이전트 ID가 계속 유효하다고 가정하지 않는다.
- 문서와 역할을 준비한 것은 기능 구현·출시·실기기 검증 완료를 의미하지 않는다. 외부 서비스 전송이나 배포 권한도 새로 부여하지 않는다.

준비 당시의 미구현 문구는 당시 상태다. 후속 사용자 승인으로 Sol 지휘 아래 Terra(`gpt-6.1-terra`, `/root/sol_lead/terra_s3`)가 모델·허브·통합 검사를, Luna(`gpt-6-luna`, `/root/sol_lead/luna_s3`)가 독립 모델·개인정보 검사를 수행했다. Sol(`gpt-6.1-sol`)은 UI·앱 연결·실제 영상 왕복·회귀 및 최종 통합을 맡았다. 파일별 소유권을 나누고 종료 뒤 인계했다. 계정 기본 모델·새 대화 자동 구성·클라우드 설정은 바꾸지 않았다.

## S4 검증 팀의 환경 연결 확인 — 2026-11-06

환경을 재게시·교체한 뒤 공유 workspace가 새 환경과 연결됐는지 확인할 때 root는 일회성 marker를 만들 수 있다. 이 경우 각 child agent는 marker가 준비된 뒤 첫 shell 실행에서 `hostname`과 `/workspace/scratch/s4-root-environment-probe.txt`를 읽고 Sol에게 보고한다. 이번 probe의 기대 hostname은 `c721c867aa76`, marker는 `root-current-published-environment-369e8c5a-2026-11-06`이었다. 값이 다르면 실질 작업을 시작하지 않고 Sol에게 알린다. 임시 marker는 검증 후 root가 정리할 수 있다. probe가 생성되지 않은 평상시 세션에서는 이 파일의 상시 존재를 전제하지 않는다. 이 marker는 자동화 테스트 의존성이 아니다.

이번 Luna와 Terra 검증자는 각각 첫 shell에서 두 값을 확인해 일치 보고 후 진행했다. root는 확인 완료 뒤 임시 marker를 정리했다. 이 검사는 환경 설정이나 저장소 설정 변경 없이 수행했다. 이 절차는 환경 재게시·교체 뒤 담당자의 공유 작업공간 연결을 확인하며 모델·기능 검증 근거를 대신하지 않는다.

## S4.1~S4.2 개발 검증 기록 — 2026-11-06

Sol이 공식 MediaPipe Lite 모델 자산·설치기와 기존 SDK 설정 확인을, Terra가 실제 모델 worker·짧은 동시 성능 suite를 담당했다. Luna는 공식 Model Card 이용조건을 조사하고 단위 39개 및 관련 브라우저 7종(camera, clips, smoke, pose-runtime, pose-ui, pwa, pose-real)을 독립 실행했다. 단위 39개와 해당 7종은 통과했다. 브라우저 19종 전체를 이번에 다시 실행하지 않았다. S4.1~S4.2의 개발환경 잔여 검증은 완료했으나 Android·학교 환경·40분·전체 메모리·발열·폭넓은 자세 정확도는 대기다. S4.3 이후는 시작하지 않았다.

## S4.3 실행 팀 기록 — 2026-11-06

사용자의 다음 작업 요청으로 현재 Sol·Terra·Luna 팀이 S4.3에 착수했다. 세 담당자 모두 첫 실행에서 hostname `c721c867aa76`과 임시 `/workspace/scratch/s4-3-root-probe.txt`의 `s4-3-current-root-2026-11-06` 값을 확인했다. 이 marker는 테스트 의존성이 아니며 root가 검증 뒤 정리할 수 있다.

Terra는 순수 동작 모듈·단위 검사·PoseUI와 worker 치수 연결, Sol은 교사 설정·화면·셸 v11·기존 회귀와 통합 리뷰, Luna는 독립 단위·신규 UI 통합 검사와 사용/검증 문서를 맡았다. 파일별 소유권을 분리했다. 단위 49개와 기존 관련 브라우저 11종 및 신규 UI 1종이 통과해 S4.3 개발 검증을 완료했다. 실스포츠 정확도와 실기기 검증을 개발용 결과로 대신하지 않는다. 환경 설정 재저장·게시·commit·push·외부 배포는 하지 않았다.

## S4.4 실행 팀 기록 — 2026-11-06

세 담당자 모두 hostname `c721c867aa76`과 임시 `/workspace/scratch/s4-4-root-probe.txt`의 `s4-4-root-2026-11-06-c721c867aa76` 일치를 확인한 뒤 작업했다. marker는 연결 확인용이며 테스트 의존성이 아니다.
